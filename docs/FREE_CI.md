# 무료 CI 운영 정책 (2026-10-12)

## 무료 범위와 제외 범위

GitHub는 공개 저장소의 표준 GitHub 호스팅 실행기를 무료로 안내하며, 더 큰 실행기는 항상 과금합니다. 유료 작업을 여러 단계로 나눠도 무료가 되지 않습니다. 이 저장소는 `ubuntu-24.04`, `windows-2022`, `windows-2025`, `windows-11-arm`만 허용하고, 실행기를 배정하기 전에 모든 작업에 공개 저장소 조건을 적용합니다. CI는 명시적인 실행기 레이블, 정적 매트릭스, 검토된 액션 커밋 고정값, 시간 제한과 하루 보존 기간을 검사합니다. 자동 Actions 캐시, 사용자 지정 이미지·스냅샷, LFS와 검토하지 않은 서비스 액션은 활성화하지 않습니다.

이 워크플로만으로 계정의 청구 상태나 다른 저장소의 상태를 알 수 없습니다. 이 검사는 우발적인 정책 변경을 막기 위한 것으로, 정책 자체를 바꿀 수 있는 작성자에 대한 보안 경계는 아닙니다. 소유자의 계정 전체 비용이 0이라고 보장하거나 이미 누적된 저장량을 소급 제거하지 못합니다. 산출물·Packages 저장 공간과 캐시 제공량은 별도로 고려해야 합니다.

**소유자의 보호 장치:** GitHub Billing and licensing > Budgets and alerts에서 저장소 범위의 Actions 예산을 **$0**으로 만들고, 이메일 알림만 켜지 말고 **Stop usage when budget limit is reached**(한도 도달 시 사용 중지)를 선택하세요. 예산이 실제로 과금되는 Actions 저장 공간을 포함하는지 확인합니다. 캐시 제거 한도는 기본 제공 10 GB를 유지하고 유료 추가 저장 공간을 선택하지 않습니다. 이 변경은 계정 설정을 읽거나 바꾸지 않습니다. 예산 한도로 추가 산출물이 차단될 수 있으며, 이를 피하려고 유료 용량을 활성화하지 않습니다.

## 단계

Windows 빌드 워크플로는 명시적인 수동 모드를 제공합니다. 기본값은 `full`입니다. 푸시, 태그, PR과 예약 실행은 항상 전체 모드를 사용합니다. PR은 이벤트 입력으로 검증 범위를 줄일 수 없습니다.

| 모드 | 수행 작업 | 게시 |
| --- | --- | --- |
| `checks` | 공개·무료 정책 검사, CI 회귀 테스트, 패키지·정책 테스트 | 하지 않음 |
| `engine` | 검사와 소스 빌드 WASM, 프런트엔드 테스트·빌드, 브라우저 E2E 환경 3종 | 하지 않음 |
| `full` | 엔진 검사, Windows 빌드, x64 Windows E2E·가상 인쇄 2종과 ARM64 Windows E2E·가상 인쇄, x64 MSIX 설치·전체 WACK, ARM64 네이티브 설치와 x64 SDK 전체 WACK | 모든 필수 검증이 성공하고 기존의 신뢰된 저장소·ref·이벤트 규칙이 허용할 때만 게시 |

사전 점검을 통과해야 소스 빌드 WASM을 실행합니다. 사전 점검과 WASM이 성공하면 x64의 `windows-editor`·`windows-cli`와 ARM64의 `windows-editor-arm64`·`windows-cli-arm64`가 각각 표준 실행기에서 병렬 컴파일되며 브라우저 E2E 3개도 함께 실행됩니다. `build`·`build-arm64`는 같은 아키텍처의 검증된 구성요소 둘을 결합해 실행 파일을 다시 컴파일하지 않고 패키지를 만듭니다. Windows 컴파일 시작 뒤 브라우저 실패가 발생해도 기존 최종 릴리스 검증에서 게시를 막습니다. 작업을 겹쳐 실행할 뿐, 성공 실행 시간이 줄거나 계정 전체 비용이 낮아진다고 보장하지 않습니다.

엔진은 전체 실행마다 한 번, Windows 패키지 내용물은 아키텍처별 한 번 빌드하고 **동일한 실행**의 후속 작업과 공유합니다. 네이티브 테스트 자료 중간 산출물에는 더 이상 브라우저 프런트엔드 사본을 넣지 않습니다. 네이티브·가상 인쇄 매트릭스는 각각 표준 실행기를 최대 2개 사용하며 브라우저 3종은 모두 유지합니다. 과거 진단 바이너리를 최종 후보 빌드 대신 사용하지 않습니다.

### ARM64 네이티브 설치와 전체 WACK의 필수 결합

ARM64 후보는 `msix-native-arm64`가 표준 `windows-11-arm` 실행기에서 직접
설치하여 GUI·CLI·MCP·별도 작업자 실패 격리·파일 연결·제거를 검증합니다.
이 작업은 `native-install.json`만 기록하며 최종 설치 성공이나 WACK 성공을
주장하지 않습니다. `msix-install-arm64`는 표준 `windows-2025` 실행기에서
그 네이티브 검증에 사용한 **동일한 서명 MSIX**를 원본 Microsoft x64 SDK로
검사합니다. 두 작업과 증거 결합이 모두 성공해야 기존 최종 `install.json`과
원본 WACK 증거를 만듭니다. ARM 런타임을 x64 실행기에서 설치한 것으로
대체하지 않습니다.

새 Source 전체 실행은 필수 작업 **21개**와 중간 산출물 정리 1개로 구성됩니다.
`release`와 `cleanup-transports`가 두 ARM 작업을 모두 기다리고, 릴리스
작성자는 21개 작업 각각의 같은 실행·HEAD·시도와 성공을 확인합니다.
공개 Source 자산은 기존 **22개**를 유지합니다. 네이티브 서명 운반 파일은
릴리스 자산에 추가하지 않습니다.

Store는 `package`, `store-native-arm64`, `Store WACK (x64)`,
`Store WACK (arm64)`, `qualify`의 **5개 필수 작업**을 같은 실행에서
통과해야 제출할 수 있습니다. x64 설치·SDK 작업 `store-wack-x64`는 `package`만 기다리며 ARM 네이티브
설치와 동시에 시작합니다. ARM SDK 작업 `store-wack`는 네이티브 성공 후보를
받은 뒤 진행하고, 두 SDK 작업은 x64 표준 실행기에서 동시에 실행할 수
있습니다. ARM 네이티브 검증과 전체 SDK 결과가 누락되거나
실패하면 `qualify`와 `submit` 모두 진행하지 않습니다. 기존 Source22,
Store 기본 파일 7개·공개 상태 포함 9개, 두 아키텍처의 raw12 증거,
무료 가격과 인증 후 자동 공개 조건을 유지합니다.

서명 후보 운반은 `native-install.json`, `test-only.msix`, 공개 `test.cer`
정확히 3개만 하루 보존하며, 이름에 현재 실행 ID와 시도를 포함합니다.
압축본과 압축 해제 크기는 각각 96 MiB를 넘을 수 없습니다. 개인 키가
포함된 PFX와 암호를 운반하지 않습니다. 소비자는 현재 네이티브 작업의
실제 API 성공 상태, 산출물 신원·해시, 원본 패키지와 런타임·manifest·PE
바이트, 서명 패키지 해시와 인증서 thumbprint를 다시 결합합니다.
SDK 누락, 선택 항목 경고나 부분 실행, 네이티브 실패, 다른 HEAD·시도,
해시 불일치 중 하나라도 있으면 전체 후보는 실패합니다. Source 운반본은
기존 전체 묶음 재검증과 모든 소비 작업 성공 뒤에만 정리하며 실패·PR
입력 보존 규칙을 그대로 적용합니다.

### 빌드 진행 로그와 자원에 따른 병렬 수

편집기 작업은 같은 실행기에서 소스·프런트엔드 준비, 네이티브 검사, 릴리스
컴파일·구성요소 보존으로 나눕니다. 기존 디버그 검사·특성 그래프 분리·고정
잠금 파일·시험 문서를 유지하며, 이전 단계가 실패하면 다음 컴파일과 capture를
진행하지 않습니다. 각 단계의 stdout·stderr 원본 로그는 16MiB 상한으로
수집하고 하루 보존합니다. 상한을 넘긴 로그를 잘라 성공으로 처리하지 않습니다.

고정한 upload-artifact v4는 업로드가 끝난 체크포인트를 전체 작업 완료 전에
API로 내려받을 수 있습니다. 실행 중인 한 Cargo 프로세스의 콘솔을 REST
완료 로그 API에서 읽을 수 있다는 뜻은 아닙니다. 별도 Checks 쓰기 권한이나
러너 내부 토큰을 추출하는 경로를 추가하지 않습니다.

컴파일 명령마다 논리 코어 수와 가용 메모리를 다시 관측하고, 1초 간격의
CPU 원시 카운터 두 값으로 현재 부하를 계산해 Cargo 병렬 수를 선택합니다.
논리 코어가 하나이면 1개를 유지합니다. CPU 부하가 90% 이상이면 1개,
75~89%이면 최대 2개, 26~74%이면 논리 코어 수 이내에서 선택합니다.
25% 이하이면 기본적으로 논리 코어 수의 두 배까지 허용하되 전체 상한은 8개입니다.
총 메모리 14GiB 이상에서 OS 여유 2GiB를 남기고 동시 컴파일 작업 하나당
1.25GiB를 계산 예산으로 사용해, CPU와 메모리가 모두 허용하는 가장 큰
1·2·4·8 중 하나를 선택합니다. 예를 들어 4코어·가용 메모리 12GiB 이상이면
부하가 낮을 때 8개, 메모리가 줄면 4·2·1개로 낮춥니다. 총 메모리가 14GiB
미만이거나 관측에 실패하면 최대 2개로 제한합니다. 이 예산은 실제 메모리를
예약하거나 컴파일러별 사용량을 제한하지 않습니다. 선택한 수와 자원·이유만
로그에 남기고 프로세스 인자·환경 변수는 수집하지 않습니다.

x64의 최종 CLI·편집기 릴리스 컴파일 두 명령은 CPU 부하 25% 이하와 총 RAM
14GiB 이상에서만 논리 코어 수의 세 배, 최대 12개를 선택할 수 있습니다.
이 경로는 OS 여유 2GiB와 작업당 계산 예산 0.75GiB로 1·2·4·8·12 중
가장 큰 수를 고릅니다. 4코어에서 가용 RAM 11GiB 이상이면 12개가 가능합니다.
ARM64·준비·네이티브 검사, 높은 CPU 부하·알 수 없는 관측·작은 실행기는
기존 8개 상한과 1.25GiB 예산을 유지합니다. GitHub Actions의 x64 릴리스
override는 현재 소유 저장소의 명시적인 공개 이벤트만 허용하며, 로컬 개발도
계속 지원합니다.

같은 고정 소스·Rust·원본 명령을 사용한 무료 표준 실행기의 cold 진단
[x64 실행 78](https://github.com/ATLKR/OpenGeul/actions/runs/38241894100)과
[ARM64 실행 79](https://github.com/ATLKR/OpenGeul/actions/runs/38242298490)에서
12개 컴파일이 모두 성공했습니다. 아래는 준비 시간을 제외하고 의존성·Skia
다운로드를 포함한 부모 컴파일 명령의 관측 시간입니다.

| 작업 | 8개 | 12개 | 16개 |
| --- | ---: | ---: | ---: |
| x64 CLI | 1198.875초 | 854.312초 | 1293.859초 |
| x64 편집기 | 1036.750초 | 963.796초 | 1007.265초 |
| ARM64 CLI | 1013.437초 | 1010.281초 | 1011.157초 |
| ARM64 편집기 | 641.969초 | 696.203초 | 745.437초 |

2초 간격으로 관측한 시스템의 최소 여유 RAM은 전체 12건에서 7.976GiB였습니다.
각 조건을 한 번 측정했으므로 네트워크·실행기 차이와 작업 병렬 수의 효과를
분리해 확정하지 않습니다. x64 릴리스의 조건부 12개만 후보로 적용하며,
ARM64와 네이티브 검사에는 확대하지 않습니다. 이 진단은 제품 실행·전체
WACK·Source20·Source22·Store 제출 자격을 대신하지 않습니다.

이미 실행 중인 Cargo의 jobserver를 변경하거나 컴파일을 종료·재시작하지
않습니다. 다음 명령은 새 관측값으로 늘리거나 줄일 수 있습니다. Source71의
기존 Editor 전체 작업 시간은 x64 약 39분, ARM64 약 37분이었으며 그 안의
릴리스 컴파일은 각각 19분48초·16분32초였습니다. 변경 후 실제 Windows에서
단계별 원본 로그·경과 시간을 다시 확인해야 속도 개선을 판정할 수 있습니다.

PR 업데이트는 같은 PR의 이전 실행을 취소합니다. main 릴리스 실행은 기존의 중단하지 않는 동시 실행 동작을 유지하므로 업로드 도중 게시가 취소되지 않습니다. 문서만 변경하면 무거운 워크플로를 실행하지 않습니다. 일반 결과는 성공한 스크린샷을 모두 복사하지 않고 로그와 작업 요약에 기록합니다.

## 저장 공간 상한

각 증거 작업은 출력을 별도로 준비합니다. 색인을 포함해 성공 시 최대 **1 MiB**, 실패·취소 시 최대 **12 MiB**입니다. 루트 JSON·JUnit 결과를 먼저 보존하고 실패 사례 증거를 우선합니다. 크기가 초과하거나 지원하지 않는 파일, 모든 원본 문서·글꼴·키는 제외하며 누락을 기록합니다. 증거를 묶으면서 실패한 테스트 상태를 바꾸지 않습니다. 실패 추적은 글꼴과 압축 해제 크기 제한을 확인합니다. 기존 원시 증거는 실행기의 임시 작업 공간에 남기며 다른 실행의 자료를 지우지 않습니다.

공개 소유 저장소의 푸시·수동 실행에서 가상 인쇄 8개 사례가 모두 성공하면, 일반 증거 묶음과 별도로 **고정 합성 PDF 7개와 manifest 1개만 총 8 MiB 이내**로 하루 보존합니다. 세 기존 인쇄 작업 각각에 하나씩 전송하며 취소 사례의 PDF는 없어야 합니다. 수집기는 현재 소스·실행·시도·작업·아키텍처와 생성한 합성 입력, 원본 보존 기록, 실제 네이티브 런타임, PDF 검사·바이트 해시를 결합합니다. 링크·Windows reparse point, 누락·변경한 PDF, 다른 실행의 기록이나 크기 초과는 실패합니다. 이 전송은 독립 재렌더링을 위한 원본을 제공하며 원본 문서·글꼴 파일·키·PNG를 추가 수집하지 않습니다. 일반 증거 whitelist, 원래 인쇄·스풀러·픽셀 기준과 필수 Source 21개·공개 자산 22개·전체 WACK 판정은 유지합니다.

업로드 전 각 중간 산출물 디렉터리의 크기를 제한합니다. 재빌드 WASM 32 MiB, 브라우저 입력 64 MiB, 편집기 구성요소 64 MiB, CLI 구성요소 32 MiB, Windows 패키지 출력 96 MiB, 네이티브 테스트 자료 16 MiB입니다. 프로토콜 2 CLI 구성요소는 실행 파일을 결정적인 gzip으로 저장하므로 32 MiB 제한은 압축 실행 파일과 메타데이터에 적용합니다. 복원된 원시 CLI와 결합한 논리적 패키지 내용물은 각각 96 MiB 이내여야 합니다. 결합 시 전체 단일 gzip 멤버, CRC·스트림 끝, 원시 크기, SHA256과 x64 PE 헤더를 검증합니다. 상한을 초과하면 더 많이 조용히 업로드하지 않고 실패합니다. 모든 업로드는 압축 수준 9와 하루 보존을 사용합니다. 이는 업로드별 상한이며 **계정 전체 저장 공간을 예약하거나 보장하지 않습니다**. 여러 실행과 다른 저장소가 제공량을 공유할 수 있습니다. GitHub Releases에는 실제 릴리스할 바이너리만 넣고 임의의 캐시 파일을 넣지 않습니다.

임시 중간 산출물 정리는 소유한 공개 저장소의 첫 실행 시도, 완전히 검증된 동일 실행 산출물 묶음과 필수 소비 작업 성공으로 제한됩니다. 실패 실행은 입력을 보존하고, 성공 PR은 게시하지 않은 Windows 패키지를 보존하며, 테스트 증거는 정리 대상으로 선택하지 않습니다. 삭제 전에 선택한 각 산출물을 다시 검증하며 다른 실행의 산출물이나 Release 자산을 제거하지 않습니다.
