# Telemetry 준비 계획

작성일: 2026-10-11. 상태: 설계 검토용 문서이며 구현·수집·배포 승인을 뜻하지 않습니다.

**다음 1.1.3 릴리스에는 Telemetry 런타임, SDK, 이벤트 수집, 수집 서버 주소(endpoint)를 추가하지 않습니다.** 이 문서는 이후 필요성을 판단하고, 별도 동의를 거쳐 구현할 경우의 최소 조건을 정리합니다. 여기 적힌 이벤트와 보존 기간도 제안이며 현재 제공되는 기능이나 운영 중인 정책이 아닙니다.

## 목적과 도입 판단

목표는 문서 열기, PDF 내보내기, 인쇄에서 발생하는 실패 유형을 집계해 수정 우선순위를 정하는 것입니다. 사용자 추적, 광고, 문서 분석, 개인별 사용 기록, 사용자 수나 재방문율 측정은 목적에 포함하지 않습니다.

도입에 앞서 개인정보 없는 재현용 문서, 자동화된 회귀 테스트와 사용자가 직접 보내는 오류 보고로 해결할 수 있는지 평가합니다. 이 방법으로 충분하면 Telemetry를 도입하지 않습니다. 도입하더라도 동의한 사용자의 작업 이벤트만 측정하므로 전체 사용자·문서·설치 수를 대표한다고 해석하지 않습니다.

| 질문 | 최소 측정값 | 판단과 한계 |
| --- | --- | --- |
| 특정 공개 버전에서 PDF·인쇄 실패가 늘었는가? | 버전·작업별 성공 및 실패 이벤트 수 | 실패 비율은 `실패 / (성공 + 실패)`로 계산합니다. 취소는 별도로 보고합니다. 같은 사용자의 반복 작업, 동의 편향과 전송 누락을 구분할 수 없습니다. |
| 다음에 어느 실패 범주를 조사할 것인가? | 작업별 허용된 실패 범주의 집계 | 집계는 조사 대상을 고르는 자료입니다. 문서 재현과 회귀 테스트가 있어야 수정 효과를 판단할 수 있습니다. |
| 수집의 편익이 비용을 정당화하는가? | 수집으로 시작한 조사 중 재현·수정으로 이어진 건수, 운영 비용 | 시범 운영 종료 시 판단합니다. 조치에 쓰이지 않거나 운영·개인정보 부담이 크면 중단합니다. |

소수 표본을 근거로 품질 개선을 단정하지 않습니다. 외부 공개 집계는 해당 범주의 이벤트가 20건 이상인 경우로 제한하는 안을 검토하며, 이 기준이 개인 식별 위험을 없앤다고 보장하지 않습니다.

## 동의와 해제

미래 구현의 기본값은 **꺼짐**입니다. 기존 설치나 업데이트에서도 자동으로 켜지지 않으며, 문서를 열거나 Store 업데이트 확인을 허용한 것을 Telemetry 동의로 취급하지 않습니다.

- 설정에서 목적, 실제 전송 필드, 처리 주체·국가, 보존·삭제 방법을 한국어로 확인한 뒤 사용자가 별도로 켭니다. 미리 선택된 체크 상자를 사용하지 않습니다.
- 동의하지 않아도 문서 열기·편집·저장·PDF·인쇄와 업데이트 확인을 사용할 수 있습니다.
- 동의 상태는 로컬에 저장합니다. 동의 설명의 버전도 로컬에만 두며, 별도의 동의·사용자 식별 이벤트를 전송하지 않습니다.
- 설정에서 같은 수준의 접근성으로 끌 수 있어야 합니다. 끄는 즉시 새 이벤트 생성과 전송을 막고, 대기 중인 이벤트를 폐기합니다. 전송 직전에도 동의 상태를 다시 확인합니다.
- 이미 전송이 시작된 요청은 서버에 도착할 수 있으므로, 해제가 과거 전송까지 취소한다고 안내하지 않습니다. 동의 해제와 보존 기한에 따른 삭제를 구분합니다.
- 수집 목적·필드·처리 주체가 바뀌면 기존 동의로 확대하지 않습니다. 수집을 중지하고 변경 내용을 설명한 뒤 새 동의를 받아야 합니다.

설정 문구의 초안은 다음과 같습니다. 실제 호스팅과 보존 정책이 확정되기 전에는 제품에 넣지 않습니다.

> 선택한 작업의 성공·실패 범주를 보내 OpenGeul의 오류를 개선하는 데 도움을 줍니다. 문서 내용, 파일 이름·경로, 비밀번호와 클립보드는 보내지 않습니다. 꺼도 앱 기능을 사용할 수 있으며 언제든 해제할 수 있습니다. 전송 항목과 보존·삭제 방법을 확인한 뒤 켜 주세요.

## 최소 이벤트와 스키마 초안

첫 시범 범위는 작업 완료 시의 `operation_result` 한 종류입니다. 화면 이동, 키 입력, 앱 실행, 문서 목록, 문서 이력, 사용 시간과 충돌 덤프를 수집하지 않습니다. 문서 자체를 구분하거나 여러 작업을 연결할 식별자도 만들지 않습니다.

| 필드 | 허용 값 | 목적 |
| --- | --- | --- |
| `schemaVersion` | 정수 `1` | 수신 형식을 엄격하게 검증 |
| `eventName` | `operation_result` | 이벤트 종류 고정 |
| `appVersion` | 배포한 OpenGeul 공개 버전의 허용 목록 | 버전별 회귀 조사. 임의 문자열·개발 환경 정보 제외 |
| `distribution` | `store`, `portable` | 배포 방식에 따른 차이 조사 |
| `operation` | `open_document`, `export_pdf`, `print_document` | 작업 범위 구분 |
| `outcome` | `success`, `failed`, `cancelled` | 완료 상태 구분 |
| `errorClass` | `none`, `parse_failed`, `render_failed`, `write_failed`, `print_failed`, `permission_denied`, `unsupported`, `other` | 미리 정한 실패 범주만 집계 |

`success`·`cancelled`에는 `errorClass=none`만 허용합니다. 실패도 코드의 정해진 분류표로 변환하며, 알 수 없는 오류는 `other`로 처리합니다. 오류 메시지에서 문자열을 추출해 전송하지 않습니다. 각 작업의 시작·완료 정의와 분류표는 구현 전에 별도 검토해야 하며, 사용자가 확인을 취소한 작업을 실패로 계산하지 않습니다.

클라이언트는 위 7개 필드만 보내는 방식으로 설계합니다. 자유 형식 속성, 중첩 객체, 추가 필드와 임의 문자열은 허용하지 않습니다. 서버도 동일한 허용 목록을 검사하고 위반 요청을 저장하지 않아야 합니다. 이벤트 한 건의 본문은 최대 512바이트로 제한하는 안을 검토합니다. 아래는 형식 설명용 예시이며 실제 전송 기록이 아닙니다.

```json
{
  "schemaVersion": 1,
  "eventName": "operation_result",
  "appVersion": "향후 승인된 공개 버전",
  "distribution": "store",
  "operation": "export_pdf",
  "outcome": "failed",
  "errorClass": "render_failed"
}
```

예시의 `appVersion` 설명 문자열은 실제 허용 값이 아닙니다. 배포 시 승인한 버전 목록에 대해서만 수신하도록 구현해야 합니다.

## 수집에서 제외할 정보

아래 항목은 본문·요청 주소·헤더·로그·오류 보고 어디에도 앱이 추가하지 않는 조건입니다. SDK의 기본 수집 필드에도 같은 기준을 적용합니다.

- 문서 내용, 텍스트, 이미지, 표, 문서 메타데이터, 문서 길이와 페이지 수
- 파일 이름·전체 경로·최근 문서 목록·문서 이력·출력 경로와 프린터 이름
- 문서 비밀번호, 입력값, 클립보드, 스크린샷, 충돌 덤프, 원문 오류 메시지
- 사용자 ID, 계정, 이메일, 장치·설치·세션 ID, 광고 ID, 문서 해시 및 식별용 난수
- IP 주소의 앱 본문 수집, OS 세부 빌드, 하드웨어 정보, 설치 글꼴 목록, 언어·위치, 정확한 클라이언트 시각

전송 경로의 서버와 HTTPS 제공자는 연결 IP와 요청 시각을 볼 수 있습니다. 따라서 위 제외 목록만으로 완전한 익명성을 주장할 수 없습니다. 네트워크와 호스팅 로그의 처리는 아래 운영 조건에서 따로 제한합니다.

## 전송·호스팅·운영 조건

호스팅 제공자, 처리 지역과 수집 주소는 **미정**이며, 이 문서에서는 서버를 만들거나 주소를 예약하지 않습니다. 미래 도입 전 다음 사항을 문서화하고 확인해야 합니다.

1. 처리 책임자와 연락처, 제공자·하위 처리자, 처리 국가 및 국외 이전 안내, 접근 권한을 확정합니다.
2. 공개된 고정 HTTPS 주소만 사용합니다. 문서·경로·식별자를 URL이나 헤더에 붙이지 않으며, 요청에 쿠키·계정 인증 정보를 넣지 않습니다. 연결 오류가 문서 작업을 실패시키거나 UI를 막지 않아야 합니다.
3. 이벤트는 동의 후 메모리에서만 잠시 보관하는 안을 우선합니다. 파일·문서 이력에 저장하지 않으며, 오프라인 이벤트를 쌓아 나중에 보내지 않습니다. 한 프로세스의 대기열 최대 20건, 시간당 전송 최대 20건, 재시도 없음으로 제한하는 안을 검토합니다. 초과분과 종료 시 대기열은 폐기합니다.
4. 요청 본문·헤더의 일반 접근 로그를 끕니다. IP와 요청 시각을 처리하는 제공자의 보안 로그는 목적·기간·삭제 가능 여부를 확인합니다. 앱 이벤트 저장소에 IP·원본 헤더를 복사하지 않습니다.
5. 개발자 접근 권한을 최소화하고, 집계 화면과 원시 저장소의 접근을 분리합니다. 민감한 값이 섞인 요청은 저장하지 않고 거절하며, 거절 로그에도 본문을 남기지 않습니다.
6. 수집 중지 기능과 처리 장애 시의 폐기 동작을 확인합니다. 서비스가 없어도 앱이 정상 동작해야 합니다. 지속 식별자 없이 남용 제한을 어떻게 운영할지도 검토하고, IP를 장기 보관하는 우회 설계를 피합니다.

SDK를 사용할지는 결정하지 않았습니다. 기본적으로 장치 ID, 자동 이벤트, 스택 추적이나 세션 추적을 추가하는 SDK는 그대로 도입하지 않습니다. 간단한 직접 전송과 SDK를 비교하되, 실제 의존성·네트워크 동작·라이선스를 검토한 뒤 별도 승인합니다.

## 보존과 삭제의 제안

| 자료 | 제안하는 최대 보존 | 삭제 조건과 검증 |
| --- | --- | --- |
| 허용된 원시 이벤트 | 수신 후 7일 | 자동 만료. 서버 수신 시각은 만료 계산에만 사용하고 장기 집계에는 날짜 단위만 남김 |
| 날짜·버전·배포 방식·작업·결과·실패 범주별 집계 | 90일 | 자동 만료. 원시 요청이나 식별자와 연결하지 않음 |
| 제공자 보안·접속 로그 | 7일 이내 | IP가 남는 범위와 실제 설정을 확인. 이 제한을 충족할 수 없으면 도입 보류 또는 새 정책 검토 |
| 백업 | 원시 이벤트·접속 로그는 백업 대상에서 제외 | 포함되는 집계 백업은 7일 이내 삭제. 운영 집계의 만료 후에도 백업에서 남을 수 있는 최대 7일을 안내 |

현재 이 삭제 작업을 운영하고 있다는 뜻은 아닙니다. 삭제 스케줄, 실패 알림과 복원 후 재만료 동작은 도입 전에 검증해야 합니다. 시범 운영을 종료하거나 수집 목적을 철회하면 원시 이벤트·집계·해당 백업을 정리하고 삭제 결과를 기록합니다.

개별 사용자 식별자를 저장하지 않으므로, 과거 이벤트를 특정 사람의 기록으로 찾아 삭제하거나 자료를 열람시키는 기능은 이 설계로 제공할 수 없습니다. 동의를 끄면 향후 전송을 중단하고 로컬 대기열을 비웁니다. 과거 이벤트는 위 짧은 보존 기간으로 삭제하는 한계를 동의 화면에 명확히 설명해야 합니다. 문의 창구는 [allenlim@allenlim.net](mailto:allenlim@allenlim.net)이며, 요청을 위해 문서·비밀번호·기기 식별 정보를 보내도록 요구하지 않습니다. 개별 삭제가 필요한 요구를 충족할 수 있는지 개인정보 검토를 마친 뒤 도입 여부를 결정합니다.

## Store 공개 버전 확인과의 경계

공개 Store 버전 정보를 고정 HTTPS 주소에서 **GET으로 읽는 업데이트 확인은 위 Telemetry 이벤트 전송과 별개**입니다. 앱 작업 결과를 수집하는 기능으로 확장하거나, 업데이트 확인 설정을 Telemetry 동의에 묶지 않습니다. 공개 버전 확인에서도 문서 내용·경로·비밀번호·클립보드·사용자 ID를 보내지 않아야 합니다.

그 GET 요청에도 IP, 접속 시각과 HTTPS 요청 정보가 호스팅 제공자에 전달될 수 있습니다. 공개 JSON을 읽는다는 이유로 네트워크 전송이 없다고 설명하지 않습니다. 수동·자동 확인 여부와 빈도, 고정 주소, 호스팅 로그의 범위는 실제 구현에 맞춰 개인정보 처리방침에 따로 안내해야 합니다. Microsoft Store 앱을 여는 동작에는 Microsoft의 처리도 적용됩니다.

이 문서는 자동 버전 확인이나 Telemetry가 이미 구현·배포됐다는 주장에 사용하지 않습니다. 현재 앱·웹사이트의 실제 처리에 관한 안내는 [개인정보 처리방침](PRIVACY.md)을 기준으로 하며, 기능 변경 시 그 안내를 먼저 일치시켜야 합니다.

미래 구현의 출시 검증은 다음 관찰 가능한 결과를 요구합니다.

- 기본 꺼짐과 거절 상태에서는 Telemetry 목적지로 DNS·HTTPS 요청이 발생하지 않습니다. 별도 Store GET 요청은 구분해 확인합니다.
- 동의 후 실제 전송을 캡처해 7개 허용 필드만 있는지 확인합니다. 특수한 파일명·경로, 비밀번호, 클립보드, 문서 텍스트와 오류 메시지를 넣어도 어떤 전송·로그에도 나타나지 않아야 합니다.
- 동의 해제 시 대기열과 전송 직전 검사를 확인합니다. 재시작·업데이트·설정 마이그레이션이 동의를 자동으로 켜지 않아야 합니다.
- 서버가 추가 필드, 큰 본문, 잘못된 버전·열거 값을 저장하지 않고 거절하는지 확인합니다. 거절 시 본문이 로그에 남지 않아야 합니다.
- 오프라인·TLS 실패·서버 오류·시간 초과·전송량 초과에서 문서 작업이 정상 완료되고, 재시도나 디스크 대기열이 생기지 않아야 합니다.
- 실제 만료, 접근 로그 설정, 백업 제외·만료, 서비스 중지 후 폐기를 확인합니다. 설명 문구·개인정보 처리방침·Store 공개 내용과 검증한 동작이 같아야 합니다.

이 조건은 미래 도입 검토용입니다. **1.1.3의 릴리스 조건은 Telemetry 준비 문서만 포함하고 수집 기능을 추가하지 않는 것**이며, 이 문서를 넣었다는 이유로 이벤트 수집을 시작하지 않습니다.
