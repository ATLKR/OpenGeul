# OpenGeul Office ARM64 and functional verification

The next portable development milestone is 0.2.0-dev for Windows x64 and native
ARM64. It extends the verified 0.1.1-dev source at
80c722c00377189495c3731c3b507d402bbbb6c2. Existing main, Store configuration and
published/draft releases remain separate. Delivery uses a new unpublished draft;
no public release or main merge is part of this work.

## Architecture

Keep one Suite source and worker implementation. The native .NET shell, Office
runtime, Python/UNO, CRT and HWP executable must match the selected architecture.
The x64 lock stays at suite/config/runtime.lock.json; the new ARM64 lock is
suite/config/runtime.arm64.lock.json. Both start from upstream Office 26.8.1.1 and HWP
1.1.4, with authenticated size/SHA256 and corresponding source. The official
ARM64 MSI is a baseline/control input: it disables embedded Firebird. The user
explicitly chose a source-built, fully native Base engine; emulation and a reduced
Base module cannot satisfy this milestone. The native source build must correct
proven CPU/configure defects and pass actual Firebird and Base persistence tests. Build arguments
accept only x64 or arm64. No x64 host is advertised as a native ARM64 component.
Optional upstream cross-platform executable templates require exact per-path,
per-machine, per-hash admissions. Wrong architectures fail before delivery.

Payload inventory, provenance and the lock in the exact source archive must
agree. The existing x64 default APIs remain compatible. MSI CRT extraction
selects the native File IDs from authenticated cabinets rather than flattened
administrative extraction filenames.

## Verification

Run the existing native editor, Korean UI/IME, saved-content, lifecycle and
startup gates on both native architectures. The controller, in-process IME
observer and registered Microsoft IME must have the same native architecture.
Retain original failures, raw observations and cleanup evidence; do not turn a
missing runtime, input method or failed case into a skip or passing result.

Add a feature catalogue with every advertised Office format mapping. A new
engine E2E suite covers all 15 format mappings plus six richer module cases:
Writer formatting/table, Calc multi-sheet/formula, Impress slide structure,
Draw page/shape geometry, Math formula edit, Base SQL CRUD/rollback. Text and CSV
are tested against their explicit plain-text/value semantics, not unsupported
rich formatting. Engine tests are labelled separately from physical GUI tests.
Each case writes evidence even after failure; incomplete case coverage fails.

An Office replacement has an open-ended feature space. The catalogue must state
which features were actually executed, what the oracle checked, and what is
unsupported or unverified. Neither this milestone nor a green test count means
universal Microsoft/Hancom compatibility or all Office features are complete.

## Acceptance

Both clean native builds, full payload verification, unchanged required x64
gates, corresponding ARM64 gates and all new semantic cases must succeed before
calling the paired milestone release-ready. Deliver evidence and Korean usage
notes with exact source, architecture, run, asset sizes and hashes. Existing
0.1.1-dev artifacts remain untouched. HWP continues in its accepted separate
window. Calc cell editing must be committed before Save.
